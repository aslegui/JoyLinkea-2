# Backends Windows para JoyLinkea-2 V1 — investigación dirigida

**Decisión vigente (2026-09-23):** HIDMaestro 1.9.0 con Controller Host + Safety Watchdog es el backend nativo V1 aprobado y el modo normal predeterminado, bajo el contrato de fallos individuales y exclusividad de sus dispositivos. El harness aislado pasó `T0→TxinputSafe <=500 ms` para A (75,481 ms), RT (76,337 ms), left stick (77,067 ms) y muerte del Watchdog con A (0,669 ms). El runtime productivo, con A enviado por WebSocket→Node→IPC, midió **76,8035 ms** tras crash del Controller Host y volvió al baseline XInput/PnP. Fake se selecciona explícitamente para desarrollo/tests; ViGEmBus permanece suspendido. Esta sección histórica de investigación no sustituye el [checkpoint](NATIVE_BACKEND_CHECKPOINT.md) ni el [ADR](ADR-0001-hidmaestro-v1.md).

**Intento histórico con detección asíncrona:** el primer rescate con A activo encontró A retenido ~1,49 s y Watchdog detectó la muerte ~1,52 s después. Ese mecanismo de espera se reemplazó por el handle directo; sus tiempos no describen la implementación actual. Ver [checkpoint](NATIVE_BACKEND_CHECKPOINT.md).

**Decisión de dirección (2026-09-23):** el usuario retomó HIDMaestro 1.9.0 como candidato nativo principal y suspendió las pruebas/integración de ViGEmBus. El objetivo ahora es medir experimentalmente rescate mediante Controller Host + Safety Watchdog para fallas individuales; JoyLinkea acepta exclusividad de dispositivos virtuales HIDMaestro durante su operación. Esta decisión de dirección **no aprueba** el backend. El primer ensayo aislado se detuvo antes del rescue por una aserción de neutralidad demasiado estricta en el harness; ver [checkpoint](NATIVE_BACKEND_CHECKPOINT.md).

Fecha: 2026-09-23. La matriz original fue una revisión documental y de código, anterior a la decisión V1; los resultados nativos posteriores se resumen arriba y en el checkpoint.

**Actualización del checkpoint (2026-09-23):** el usuario instaló ViGEmBus 1.22.0 manualmente. La fase 0 de JoyLinkea verificó instalador registrado, driver Nefarius iniciado, interfaz habilitada y baseline XInput 0 ocupado / 1–3 libres. Encontró además una instancia `HID\HIDMaestro` desconectada de pruebas anteriores; por el requisito de ausencia de cualquier residuo virtual, se detuvo **antes de crear controles**. No existe aún medición de crash-safety ViGEmBus. Ver [checkpoint nativo](NATIVE_BACKEND_CHECKPOINT.md).

**Avance posterior:** el usuario aceptó explícitamente esa instancia HIDMaestro desconectada como baseline preexistente. El primer control ViGEmBus apareció en XInput índice 1, pero la primera lectura tras `ResetReport()`/`SubmitReport()` tuvo sticks distintos de cero (`LX=-3356`, `LY=-1869`, `RX=-3255`, `RY=-848`). Se ordenó una neutralización y destrucción normales, XInput volvió al baseline y no quedó nuevo PnP conectado; sí se registraron tres instancias nuevas desconectadas. **Fase 2 detenida; no se ejecutó kill ni se midió crash-safety.** Causa de la lectura inicial aún no determinada. Detalle en [checkpoint nativo](NATIVE_BACKEND_CHECKPOINT.md).

## Criterio y lenguaje de evidencia

El requisito decisivo es que, ante muerte abrupta del proceso que alimenta A, RT o un stick, Windows deje de observar ese input en un plazo acotado y razonable. Desconectar el dispositivo satisface el requisito solo si XInput/juego deja de observarlo; dejarlo enumerado en neutral también puede satisfacerlo. Cleanup posterior sirve para recuperar el sistema, pero no equivale a seguridad durante el intervalo previo.

En la matriz original, **CONFIRMADO** significa comprobado en el checkpoint local o directamente presente en código/API oficial de la versión indicada; cuando se trata de código, **no implica que se haya validado en esta PC**. **NO SOPORTADO** significa que el backend por sí solo carece de la capacidad indicada. **NO VERIFICADO** incluye claims sin medición. Los tiempos posteriores de HIDMaestro + Watchdog son una propiedad de esa arquitectura compuesta, no del driver solo.

## Evidencia específica de crash-safety

**HIDMaestro.** El checkpoint local observó A presionado inmediatamente después de matar abruptamente el Bridge propietario. El dispositivo siguió enumerado; más tarde se observó A neutral con problema PnP 43, sin medir cuándo cambió. `Dispose`, `ProcessExit` y el `IdleFrameLoop` no cubren muerte abrupta; el companion conserva `LastGoodGip` y reabre tras 500 lecturas stale, sin plazo temporal de neutralización. La API pública no adopta una `identityKey` huérfana. El barrido oficial global recuperó el residuo luego, pero **recuperación posterior no demuestra fail-safe**. [Checkpoint](NATIVE_BACKEND_CHECKPOINT.md).

**ViGEmBus.** En v1.22.0, `WDF_FILEOBJECT_CONFIG_INIT` registra `Bus_FileClose`. Allí el driver recorre los hijos presentes y llama `WdfChildListUpdateChildDescriptionAsMissing` solo si `description.SessionId == pFileData->SessionId`. La creación asigna ese SessionId a los hijos. Al morir el proceso, Windows cierra su handle y se solicita desenchufar sus controles sin ejecutar código de usuario. Esto es un mecanismo más fuerte que `Dispose`; **no hay timeout de input separado ni máximo publicado de finalización PnP/XInput**. El cierre de handle podría verse demorado por handles duplicados; revisar en checkpoint. No ofrece adopción estable de un dispositivo huérfano como estrategia primaria. [Código v1.22.0](https://github.com/nefarius/ViGEmBus/blob/v1.22.0/sys/Driver.cpp).

**libvirtualhid.** En el tag examinado, el broker obtiene el PID del cliente por named pipe, abre un process handle con `SYNCHRONIZE`, registra cada dispositivo con ese handle y `cleanup_devices()` consulta `WaitForSingleObject(..., 0)`. Al observar salida o error destruye **solo** los registros de ese cliente; si falla el destroy, los conserva para reintento. Para Xbox 360, crea un `SwDevice` propiedad del broker; Windows deja de enumerarlo al cerrarse el handle, conforme a la vida `SwDeviceLifetimeHandle` predeterminada. Si muere el broker, ese handle debería cerrarse por Windows, pero la desconexión XInput y su plazo siguen sin prueba real. El bucle del broker espera conexiones de pipe con timeout configurado de 1000 ms y puede ocupar tiempo adicional en operaciones; no constituye cota dura. La ruta XUSB es nueva, usa interfaz/IOCTL no documentados públicamente por Microsoft y el propio proyecto exige regresión instalada por release. Además el driver/servicio/MSI son LB-SAL: no se deben empaquetar con JoyLinkea ni usar comercialmente sin términos del titular. [Broker](https://github.com/LizardByte/libvirtualhid/blob/v2026.921.44.4/src/platform/windows/broker/libvirtualhid_broker.cpp), [vida SwDevice](https://learn.microsoft.com/en-us/windows/win32/api/swdevice/nf-swdevice-swdevicesetlifetime), [licencia](https://github.com/LizardByte/libvirtualhid/blob/v2026.921.44.4/LICENSES/LicenseRef-LizardByte-SAL-1.0.md).

**WinUHid.** El driver configura `WinUHidEvtDeviceFileClose`, vacía solicitudes pendientes y llama `VhfDelete(vhfHandle, TRUE)` para el dispositivo ligado a ese file object. Su test Xbox One llama `XInputGetState` para verificar triggers, por lo que descartarlo como mero HID genérico sería incorrecto. Falta confirmar que los controles creados allí ocupen consistentemente un slot XInput en Windows 10 y 11, que el cierre abrupto termine la observación de input dentro del plazo elegido y que exista un paquete firmado utilizable. El INF permite abrir el enumerador a administradores, SYSTEM y UMDF, no a usuarios de escritorio ordinarios. [Driver](https://github.com/cgutman/WinUHid/blob/d6cebbe/WinUHid%20Driver/WinUHid.c), [test](https://github.com/cgutman/WinUHid/blob/d6cebbe/WinUHidUnitTests/XOne.cpp), [INF](https://github.com/cgutman/WinUHid/blob/d6cebbe/WinUHid%20Driver/WinUHidDriver.inf).

**VIIPER.** El fork expone Xbox 360 mediante USB/IP y un servicio/proceso `viiper` con API TCP local y streams persistentes. El README advierte sobre controles stale y recomienda reiniciar VIIPER, lo cual no prueba neutralización al morir el feeder ni al morir VIIPER. Su instalación autónoma en Windows se declara para desarrolladores y requiere `usbip-win2`, a veces reinicio. Por complejidad y falta de garantía encontrada, no es prioridad del primer checkpoint. [Repositorio oficial del fork](https://github.com/hbashton/VIIPER).

VHF genérico, vJoy/DirectInput, Steam Input y wrappers que dependen de ViGEmBus **no son backends Xbox/XInput independientes** para esta decisión. Microsoft distingue explícitamente XUSB de HID genérico; cambiar un VID/PID HID no crea por sí solo un endpoint XInput. [Microsoft](https://learn.microsoft.com/en-us/windows/win32/xinput/directinput-and-xusb-devices).

## Recomendación documental original (histórica; superada por el checkpoint y la decisión de dirección)

Los párrafos siguientes registran la recomendación anterior a los experimentos Owner/Watchdog. **No son instrucciones vigentes**: HIDMaestro está aprobado para V1 bajo el contrato indicado arriba y ViGEmBus está suspendido. La medición QPC productiva ya se completó.

**Opción A: ViGEmBus v1.22.0 oficial, solo para checkpoint aislado.** Tiene compatibilidad XUSB conocida, binario final firmado para 10/11 y cleanup por cierre del file object implementado en el driver. Su retiro/archivo es un riesgo serio de mantenimiento, de modo que incluso un checkpoint exitoso exigiría registrar estrategia de distribución, seguridad y sustitución. No adoptar automáticamente un fork; cualquier fork necesitaría su propia revisión de código, firma y checkpoint.

**Opción B: WinUHid @ d6cebbe, experimental.** También tiene teardown ligado al file object y una prueba XInput real en su suite, con licencia MIT. Requiere resolver firma/paquete, privilegios de runtime y validar que Xbox One se comporte como XInput fiable en ambas versiones de Windows. **libvirtualhid** sería un candidato técnico adicional por su broker y XUSB, pero no es opción de distribución V1 sin acuerdo explícito de licencia y Win10 sigue siendo best effort.

**HIDMaestro queda candidato suspendido, no aprobado.** La opción Owner + Rescuer con barrido global podría reducir el riesgo de una falla simple, pero no aporta una cota intrínseca, afecta dispositivos de terceros y debe medir fallas de rescate. Una modificación pequeña del backend/driver que incorpore lease o asociación a proceso sería conceptualmente más fuerte, pero implicaría fork, firma, validación y mantenimiento propios. Aceptar que el input pueda quedar retenido indefinidamente **no cumple el requisito V1**.

**Gap crítico:** ningún candidato fue medido aquí tras kill/crash con A, RT y stick retenidos. Los mecanismos de ViGEmBus, libvirtualhid y WinUHid justifican experimento, no demuestran aún una cota temporal ni el estado visto por un juego. Antes de instalar otro driver en esta PC, preparar un checkpoint en entorno Windows aislado o baseline controlado: medir XInput y PnP antes; crear un control neutral; aplicar A/RT/stick por separado; matar solo el feeder sin ejecutar cleanup; muestrear XInput con reloj monotónico y registrar instante de neutral/desconexión, PnP, errores y controles físicos; detener al primer residuo. Repetir después con 2–4 controles y caída del proceso/servicio dueño, solo si la prueba de uno pasa. El umbral aceptable debe fijarse **antes** de probar a partir de la vigencia de input acordada para JoyLinkea, sin inventarlo a posteriori. Registrar también instalación, UAC, rollback y firma. No ejecutar esta prueba sin autorización separada.
