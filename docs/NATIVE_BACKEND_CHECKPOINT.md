## Histórico anterior: harness de seguridad y timing productivo pendiente (2026-09-23)

Se sustituyó en el harness `Process.WaitForExitAsync` + `Task.WhenAny` por espera directa del handle de proceso con `WaitForMultipleObjects`/`WaitForSingleObject`, conservando PID + hora de inicio. El monitor independiente continuó muestreando XInput durante recovery, sin usar `TrecoveryReturn` como sustituto de `TxinputSafe`. Se verificó baseline XInput 0 neutral / 1–3 libres, sin HIDMaestro conectado, antes de cada ensayo. No se instaló, reparó o limpió el driver ni se tocó ViGEmBus.

|---|---:|---:|---:|---:|---:|---|
| Owner crash + A | ≈−0,014 ms | ≈0,168 ms | ≈75,328 ms | **75,481 ms** | ≈10109,500 ms | PASS |

Los Tdetect ligeramente negativos significan que el proceso superviviente recibió la señal de terminación antes de que el monitor independiente terminara de confirmar esa misma muerte; no son detección antes de la muerte real. `T0` es confirmación del monitor, `KillRequested` también está registrado para un límite conservador. En A, la API tardó ~10,1 s en retornar, pero XInput dejó de observar A a los 75,481 ms. En los tres ensayos del Owner, XInput primero mostró el estado neutral y luego el control desapareció. PnP no se midió con resolución de milisegundos; al final no había HIDMaestro conectado. Logs: `.native-cache/hmrescue-crash-{a,rt,stick}-directwait.stdout.log`, `.exit.txt`, los `watchdog-crash-*` impresos allí y `.native-cache/hmrescue-watchdog-crash-directwait.stdout.log`.

**Integración:** `bridge/native/Program.cs` conserva el protocolo IPC y convierte el Bridge existente en Controller Host. `bridge/native/SafetyWatchdog.cs` inicia un proceso elevado independiente antes de permitir controles, verifica PID + hora de inicio y espera handles reales. Controller Host vigila recíprocamente; ante muerte del Watchdog neutraliza, destruye y sale. Shutdown normal confirma cleanup antes de enviar `DISARM`; incertidumbre deja Watchdog armado. El Watchdog solo usa `HMContext.RemoveAllVirtualControllers(preserveInstall:true)` ante muerte inesperada del Controller Host. Este barrido es global y supone uso exclusivo de dispositivos virtuales HIDMaestro por JoyLinkea. No hay reinicio automático ni cambios al protocolo web, Motion, Fake o ViGEmBus.

**Validación productiva funcional:** `test/native-end-to-end.manual.mjs` pasó con dos clientes, timeout, reconexión, gracia, pérdida de Node y baseline final. `test/native-bridge-failure.manual.mjs` pasó shutdown y crash con dos controles activos; Watchdog retiró ambos y el baseline volvió. `test/native-safety-watchdog.manual.mjs` pasó muerte individual del Watchdog: Controller Host neutralizó/destruyó y salió. `test/native-restart.manual.mjs` pasó un arranque normal después del recovery. Logs persistentes en `%LOCALAPPDATA%\JoyLinkea-2\logs` muestran `DISARMED_AFTER_OWNER_CLEANUP` para cierre normal y `RECOVERY_RETURN OK` para crash del Controller Host.

**Límite de aquel intento, ya superado:** `test/native-safety-timing.manual.mjs` intentó medir con QPC el crash productivo del Controller Host. Confirmó A activo, luego mató el proceso, pero el monitor C# lanzó una excepción al consultar `ExitCode` en un `Process` adjuntado por PID (no iniciado por ese objeto). El Watchdog registró detección y `RECOVERY_RETURN OK`; XInput/PnP volvieron al baseline, pero **ese intento no registró `TxinputSafe` productivo**. Se corrigió esa línea del monitor. El segundo caso productivo (muerte de Watchdog con medición QPC) no se ejecutó, según el alcance acordado. La medición productiva posterior está registrada al comienzo de este documento.

### Garantías examinadas en el tag exacto

- **Garantizado por la API:** `HMController.Dispose()`/`HMContext.Dispose()` hacen teardown durante un cierre que ejecuta código; `HMContext.RemoveAllVirtualControllers(bool preserveInstall)` puede barrer huérfanos globalmente desde otro proceso elevado. La variante `true` conserva instalación; el CLI oficial `cleanup` usa la variante sin parámetro (`false`). Ninguna de estas operaciones corre necesariamente cuando el proceso muere por kill/crash.
- **No encontrado para Xbox 360/UMDF2:** watchdog, lease, keepalive, timestamp de vigencia de input, ownership atado al PID ni neutralización/destrucción automática por muerte del creador. El [driver principal](https://github.com/hifihedgehog/HIDMaestro/blob/v1.9.0/driver/driver.c) ignora snapshots sin nuevo `SeqNo` (`ProcessSharedInput`). El [companion XUSB](https://github.com/hifihedgehog/HIDMaestro/blob/v1.9.0/driver/companion.c) mantiene `LastGoodGip`; tras 500 lecturas con secuencia igual reabre la sección compartida, pero sirve el último payload durante esa transición. Es recuperación de handle, no un tiempo máximo de input ni un evento de muerte del propietario. Depende además de lecturas; no prueba un límite temporal universal.
- **Distinción:** `HMController` tiene un `IdleFrameLoop` opcional que repite el **último** estado para perfiles que declaran `IdleFrameIntervalMs`. Corre dentro del proceso creador y no es un fail-safe; no debe confundirse con timeout. Hay watchdogs/heartbeats en código VR y timeouts de espera para IPC/driver, pero no constituyen un lease XInput del perfil `xbox-360-wired`.
- **Observado aquí:** inmediatamente después del kill abrupto, A seguía presionado en XInput y el dispositivo persistía. En una lectura posterior, A estaba neutral pero PnP/XInput seguían presentes (ROOT con problema 43). Solo el cleanup oficial quitó el dispositivo verificablemente. No se midió el instante de cambio a neutral; no atribuirlo a una garantía concreta del SDK.

### Decisión arquitectónica pendiente

Un supervisor externo puede detectar la muerte del Bridge y llamar al barrido global soportado, pero **no puede adoptar/neutralizar individualmente** el control huérfano por API pública. El barrido afectaría cualquier dispositivo HIDMaestro en la máquina y puede tardar o fallar; no garantiza que el input no quede activo durante el intervalo hasta ejecutar/terminar cleanup. Invertir ownership para que un proceso C# estable posea los `HMController` y Node solo envíe estados es la opción mínima para cubrir muerte de Node o de un Bridge de red: ese propietario neutraliza por lease/IPC. El Bridge C# actual ya cumple parcialmente ese papel y la pérdida de Node/IPC pasó la prueba. **Mover el mismo código a un proceso llamado “supervisor” no cubre el crash de ese propietario.** Para cumplir literalmente el criterio V1 ante muerte de *cualquier* proceso JoyLinkea se necesita un fail-safe independiente del proceso propietario, idealmente una garantía de lease/neutralización del driver/backend; alternativamente, un monitor separado con recuperación global y límites medidos reduciría riesgo, pero no constituye garantía absoluta si el monitor también falla. No implementar esa arquitectura todavía.

**Opción mínima a validar si se acepta garantía para una falla de proceso a la vez:** conservar el C# como propietario único; añadir un pequeño proceso de rescate elevado e independiente que espere el handle del propietario y, si muere, invoque `HMContext.RemoveAllVirtualControllers(preserveInstall: true)` y compruebe PnP/XInput. El propietario debe vigilar a ese rescatador y neutralizar/destruir sus controles si desaparece. El rescatador debe iniciarse antes de permitir inputs no neutrales, y la instancia de JoyLinkea debe ser exclusiva sobre HIDMaestro porque el barrido es global. Esto contiene fallas individuales si ambos monitores funcionan, pero requiere medir el tiempo hasta neutral, comprobar que la API de barrido funciona tras un kill y resolver fallas simultáneas, terminación del rescatador y barridos fallidos. Un servicio Windows con recuperación puede mejorar supervivencia del rescatador, a costo de instalación y privilegios. **No afirmar que este diseño ya cumple el criterio V1.**

Pruebas futuras, solo tras decisión y nuevo baseline: press sostenido → kill Node; press sostenido → kill worker/Bridge; press sostenido → kill propietario/supervisor; pérdida de IPC, suspensión/reanudación, watchdog vencido y falla deliberada de cleanup; medir tiempo hasta XInput neutral y desaparición PnP en cada caso, verificar 1–4 slots sin afectar controles físicos, y comprobar recuperación al reiniciar el supervisor. ## Prueba requerida antes del ADR

En una PC Windows de prueba y con consentimiento para instalar el componente, separando Setup elevado de runtime normal:

1. Registrar versión de Windows, arquitectura, controles físicos ya presentes, .NET y versión/hash del candidato.
2. Leer release notes y licencias del paquete exacto. Evitar expresamente HIDMaestro 1.8.0/1.8.1.
3. Solo con autorización expresa y en PC de prueba, ejecutar `JoyLinkBridge.dll --install` elevado. Registra certificado local e instala el componente de Windows; documentar exactamente el resultado y un procedimiento de reversión antes de continuar.
4. Ejecutar el demo oficial para `xbox-360-wired`; comprobar en `joy.cpl` y con lectura XInput. Crear cuatro controles y verificar el límite junto a controles físicos.
5. Probar cada eje, triggers separados, D-pad, A/B/X/Y, LB/RB, L3/R3 y Start/Back; comprobar polaridad Y.
6. Probar create/destroy repetido, desconectar cliente, matar Node y matar Bridge. Confirmar neutralización/cleanup y ausencia de dispositivos huérfanos después de reinicio.
7. Medir latencia y estabilidad; probar un juego compatible con hot-plug y otro que requiera conectar antes de abrirlo si es posible.
8. Solo después, decidir si el backend candidato puede adoptarse y escribir ADR con evidencia, versión, límite, privilegios, licencias y rollback. Si se adopta, integrar el Bridge elevado de forma controlada con el Host normal.
