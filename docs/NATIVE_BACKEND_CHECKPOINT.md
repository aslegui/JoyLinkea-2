## Candidato y evidencia pública

HIDMaestro es el primer candidato para una prueba aislada con C#/.NET 10 y perfil `xbox-360-wired`. Su repositorio muestra API para crear y enviar estado, soporte multi-controller y licencia MIT: https://github.com/hifihedgehog/HIDMaestro . La versión 1.9.0 corrige un fallo de 1.8.0/1.8.1 que podía impedir arrancar Windows; la selección exacta exige verificar release, firma, licencias incluidas y compatibilidad del equipo: https://github.com/hifihedgehog/HIDMaestro/releases . ViGEmBus sigue como alternativa histórica, pero está retirado: https://docs.nefarius.at/projects/ViGEm/End-of-Life/ .

**Hallazgo de privilegios:** la documentación de `HMContext` indica que tanto `InstallDriver()` como `CreateController()` requieren administrador. Un Setup elevado por única vez no alcanza para este backend; el Bridge de runtime también necesitaría elevación. El modo `native` actual es **solo experimental**, requiere `JOYLINKEA_NATIVE_EXPERIMENT=1` y no resuelve todavía un Bridge elevado con Node normal. Evaluar ese costo frente a otra tecnología antes de aprobar el backend. Fuente: https://github.com/hifihedgehog/HIDMaestro/blob/master/sdk/HIDMaestro.Core/HMContext.cs .

Preparación reproducible: `powershell -File scripts/Prepare-HIDMaestro.ps1` verifica hash y extrae DLL/licencia, sin instalar. `& 'C:\Program Files\dotnet\dotnet.exe' build bridge/native/JoyLinkBridge.csproj` compila. `& 'C:\Program Files\dotnet\dotnet.exe' bridge/native/bin/Debug/net10.0-windows/JoyLinkBridge.dll --self-test` prueba esquema/mapeo sin tocar dispositivos.

## Prueba requerida antes del ADR

En una PC Windows de prueba y con consentimiento para instalar el componente, separando Setup elevado de runtime normal:

1. Registrar versión de Windows, arquitectura, controles físicos ya presentes, .NET y versión/hash del candidato.
2. Leer release notes y licencias del paquete exacto. Evitar expresamente HIDMaestro 1.8.0/1.8.1.
3. Solo con autorización expresa y en PC de prueba, ejecutar `JoyLinkBridge.dll --install` elevado. Registra certificado local e instala el componente de Windows; documentar exactamente el resultado y un procedimiento de reversión antes de continuar.
4. Ejecutar el demo oficial para `xbox-360-wired`; comprobar en `joy.cpl` y con lectura XInput. Crear cuatro controles y verificar el límite junto a controles físicos.
5. Probar cada eje, triggers separados, D-pad, A/B/X/Y, LB/RB, L3/R3 y Start/Back; comprobar polaridad Y.
6. Probar create/destroy repetido, desconectar cliente, matar Node y matar Bridge. Confirmar neutralización/cleanup y ausencia de dispositivos huérfanos después de reinicio.
7. Medir latencia y estabilidad; probar un juego compatible con hot-plug y otro que requiera conectar antes de abrirlo si es posible.
8. Solo después, decidir si el backend candidato puede adoptarse y escribir ADR con evidencia, versión, límite, privilegios, licencias y rollback. Si se adopta, integrar el Bridge elevado de forma controlada con el Host normal.

Hasta completar esto, JoyLinkea-2 **no está verificado como gamepad de Windows**.
